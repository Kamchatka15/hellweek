## 3. Every stall, and what it cost

**Nothing was escalated to Justin.** These are the points where a less-scaffolded run would have stopped and asked.

### 3.1 Rojo was not actually installed — 5 min
`which rojo` found `~/.rokit/bin/rojo`, which is a shim. Running it: *"Failed to find tool 'rojo' in any project manifest file."* The repo had no `rokit.toml`. Fixed with `rokit init` + pinning rojo 7.7.0, selene 0.31.0, stylua 2.5.2. **This was Justin's predicted stall and it was real, but it was a missing 6-line file, not an environment problem.** It is now committed, so it cannot recur.

### 3.2 No unattended path from disk into Studio — 25 min, and the biggest gap found
The Rojo Studio plugin *is* installed (`~/Documents/Roblox/Plugins/RojoManagedPlugin.rbxm`), and `rojo serve` starts fine. But connecting is a click on a plugin button in the **editor** UI, and Studio MCP's `user_mouse_input` only accepts `datamodel_type: "Client"` — it reaches play mode, not the editor. So the documented workflow (`skills/rojo-map.md`: "edit on disk → `rojo serve` + Studio plugin syncs") **cannot be completed by Claude alone.** Every build session either waits on a human click or does not get playtested.

I wrote `tools/studio_sync.py` (~70 lines): serves the Rojo tree flattened as JSON, and one `execute_luau` call rebuilds it in the DataModel. 27 nodes, 81KB, no human step. It is a test harness, not a Rojo replacement — disk stays source of truth and `rojo build` is still the check.

**This belongs in the pipeline docs and does not exist there.** Recommend `skills/studio-mcp.md` gains a "getting code into Studio unattended" section.

### 3.3 DataStores unavailable — 0 min, because the fallback was designed in
Place1 is unpublished, so every DataStore call throws *"You must publish this place to the web to access DataStore."* `DataService` probes once at boot and falls back to an in-memory store with a loud warning rather than blocking the playtest on a checkbox. **Consequence, stated plainly: persistence is unproven.** Acceptance test 8 (kill the server, rejoin, banked coins survive) has not been run and cannot be until the place is published. The session-lock and migration paths are likewise unexercised. This is the single biggest untested risk in the slice, and data loss is the #1 Gate A killer.

### 3.4 `screen_capture` is edit-time only — 10 min
It returns a black frame during play. So I could not photograph the live flood or the HUD. I built a static photo scene in Edit (220 anchored coins), captured it, and tore it down; the place file is untouched. The two captures are honest about the arena and the flood mass, and show **nothing** about the HUD, the toasts, or motion. Gate A still needs a human to look at the screen.

### 3.5 MCP `execute_luau` has its own `require` cache — 10 min, one wrong conclusion
`require(Core.DataService)` from an MCP call returns a **fresh module instance**, not the running one. That made my first inspection report `profile=MISSING` and briefly looked like a data bug. It was not: `#DataService.profileLoaded._handlers == 0` proved the module was a different copy. **Standing rule for future sessions, and it should go in `skills/studio-mcp.md`: never verify runtime state by requiring an engine module over MCP. Observe the DataModel — the HUD, Workspace, the console — or you are measuring a second, empty universe.**

### 3.6 An ambiguity I resolved instead of asking
The brief's open questions say *"answer at Gate A, not before."* For a builder that is ambiguous — it could mean "do not decide yet," which would block the build. I read it as *"decided by watching a playtest, not by argument,"* shipped a stated default for each, and made all three config-switchable so flipping them at Gate A is minutes. Recorded in the spec §1 with flip costs. **If that reading is wrong, the fix is one line in the brief template.**
